## Field `organization_suggestion`

Suggestion for how to organize the specs for this project. Read by the Aegis Spec orchestrator to pre-select the default option in the specs organization menu.

### Subfields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `granularity` | string | yes | One of: `module`, `use-case`, `endpoint`, `hybrid`, `feature`, `custom`. Scout never suggests `custom`; that value only comes from user choice. |
| `rationale` | string | yes | Short phrase explaining why that granularity was chosen. Appears in the menu as "Reason:" from Scout. |
| `signals` | array | yes | List of detected signals that led to the suggestion. Each item has `type` and `evidence` (list of paths). Can be empty when fallback `feature` is used. |
| `features` | array | yes when `granularity = "feature"` | List of discovered feature names by Scout. Each name becomes a top-level folder. |

### Heuristics for defining `granularity`

| Detected signal | Suggested `granularity` |
|-----------------|--------------------------|
| Centralized routing (`routes.*`, `urls.py`, `*Controller.cs`, `@RestController`) | `endpoint` |
| Top-level folders with domain names (`auth/`, `orders/`, `payments/`) | `module` |
| Gherkin / E2E specs oriented to behavior (`features/*.feature`, `*.spec.*` BDD) | `use-case` |
| Multiple signals coexisting with similar weight | `hybrid` |
| No clear organization signal | `feature` (fallback, populate `features` with what could be extracted) |

### Immutability

After the first run, the orchestrator persists the suggested `granularity` in `aegis/config/config.toml` in the `scout_suggestion` field. On re-runs, Scout may regenerate `surface.json` (the legacy may have changed), but the orchestrator does NOT update `scout_suggestion` in `config.toml` (RF-14 from the specs organization spec).

## Note

Use this schema as a guide. If a field doesn't apply to the project, omit it, except for the required fields listed above.
